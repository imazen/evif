# XXH3 width, stability and statistical-test evidence

XXH3-64 and XXH3-128 have stable output contracts. Both were finalized in
[xxHash v0.8.0](https://github.com/Cyan4973/xxHash/releases/tag/v0.8.0), published
July 27, 2020. The release explicitly guarantees identical outputs across systems
and future versions for the same input and parameters. Pre-0.8 experimental
outputs are not that contract. Vendoring is compatible with this guarantee;
retain default-seed/secret and serialization vectors when optimizing a port.

## Measured Rust streaming costs

Source: `cd79f4d30c0cffed264d5254d465020fd4459d49`. Same pinned zenhash
implementation and compiler as the [eight-algorithm comparison](hash-cost-2026-10-25.md).
AMD Ryzen 9 5900XT, one thread pinned to CPU 2, default runtime SIMD dispatch,
no `target-cpu=native`, thin LTO. Initialization, streaming update and finalization
are timed. Buffers are reused, not read from storage. Thirty interleaved rounds.

| Input / update size | XXH3-64 mean | XXH3-128 mean | 95% interval for relative time change |
|---|---:|---:|---:|
| 64 B / 64 B | 19.715 ns | 20.665 ns | -1.6% to +11.6% |
| 4 KiB / 4 KiB | 96.004 ns | 95.819 ns | -6.1% to +5.9% |
| 1 MiB / 1 MiB | 17.682 us | 17.417 us | -13.5% to +11.0% |
| 1 MiB / 16 KiB | 19.533 us | 19.247 us | -13.1% to +10.7% |
| 64 MiB / 64 MiB | 3.666 ms | 3.661 ms | -1.3% to +1.1% |
| 64 MiB / 16 KiB | 3.681 ms | 3.690 ms | -0.9% to +1.5% |

Bulk throughput is 17.050 versus 17.071 GiB/s for one update, and 16.977 versus
16.938 GiB/s for 16 KiB updates. No case resolves a statistically significant
speed difference. This supports negligible bulk cost in this implementation and
workload, not equal speed on every architecture or every short-message API.
The 1 MiB cases are noisier (CV 16.3–18.9%); the 64 MiB cases have CV 1.8–2.3%.
The [CSV](xxh3-widths-2026-10-25.csv) preserves all mean/MAD/CV values.

In the pinned zenhash source, both widths use the same streaming state and
accumulation. For inputs over 240 bytes, finalization uses one accumulator merge
for 64 bits and two for 128 bits. The additional finalization work does not grow
with message length. Short-input finalization uses separate width-specific paths.

The new adapter passed three constants independently checked with C xxHash 0.8.3
(empty, hello-world and deterministic 20,000-byte input), plus streaming-boundary
equivalence checks. Formatting and release Clippy passed. This is not a new
SMHasher run or exhaustive cross-platform validation.

## Which variants meet the quality requirement?

Output stability and statistical quality are separate questions. The published
[SMHasher3 table](https://gitlab.com/fwojcik/smhasher3/-/raw/main/results/README.md),
checked October 25, 2026, reports:

| Registered variant | Failed / tested cases |
|---|---:|
| XXH-32 (classic XXH32) | 83 / 250 |
| XXH-64 (classic XXH64) | 9 / 250 |
| XXH3-64 | 27 / 250 |
| XXH3-128 | 36 / 250 |
| XXH3-64.regen | 15 / 250 |
| XXH3-128.regen | 19 / 250 |

These counts are not a collision probability or a ranking of practical reliability.
The [64-bit report](https://gitlab.com/fwojcik/smhasher3/-/raw/main/results/raw/XXH3-64.txt)
includes short-input bit-independence failures, a three-byte sparse-input
differential test, PerlinNoise/Bitflip cases and several seed tests. The
[128-bit report](https://gitlab.com/fwojcik/smhasher3/-/raw/main/results/raw/XXH3-128.txt)
has overlapping failure families. For example, its three-byte sparse case reports
excess collisions in the high 40 bits of differential outputs, while full-width
hash collisions in that case are zero. This does not demonstrate collisions in
full-length image digests, but it does rule out claiming an all-tests pass.

Classic XXH64's nine reported failures are seed-related. Classic XXH32 has broader
failures and only a 32-bit digest, making it unsuitable as EVIF's sole sample
identity. `.regen` and `.reinit` are
[SMHasher3 registrations](https://gitlab.com/fwojcik/smhasher3/-/raw/main/hashes/xxhash.cpp)
that derive secrets differently; they are not universally improved replacements
for the normal algorithm. A custom secret also adds parameters that other readers
must reproduce. None of these listed variants meets a strict zero-failures gate.

For stable, interoperable, noncryptographic bulk identity, XXH3-128 is a reasonable
candidate: it buys a wider digest for negligible measured bulk cost. It does not
repair the listed statistical failures and is not a cryptographic hash. SIMD
backends are implementations of the same contract, not different-quality hash
variants. This investigation does not change EVIF's current XXH3-64 wire choice.
