# Rust hash cost and format stability, 2026-10-25

This is selection evidence, not a change to EVIF's canonical XXH3-64 samples
or optional SHA-256 checks. BLAKE3 is the preferred candidate if cryptographic
sample identity becomes a requirement; SHA-256 offers the easiest interoperability.

## Measured cost

Source: `2e6ecfbe91e2099937ee682c28d20d3859d8dbba`.
CPU: AMD Ryzen 9 5900XT (Zen 3), one hashing thread pinned to CPU 2.
Compiler: rustc 1.99.1 (58cf8f9c3 2026-10-13), LLVM 23.1.1, x86_64 Linux.
Release build, thin LTO, default crate dispatch, no `target-cpu=native` or Rayon.

Each call initializes, updates and finalizes over an already allocated buffer.
These are repeated/warm buffer measurements, not file throughput or end-to-end
EVIF decoding. Zenbench interleaved 30 rounds per case. All crypto outputs are
32 bytes; the noncrypto outputs retain their native 8/16 bytes.

The extra measured time over XXH3 for BLAKE3 is 9.940 ms per tested 64 MiB
buffer. This is hashing cost only; no claim about total codec or metric overhead.
Small-input results differ: at 64 bytes, XXH3 takes 19.626 ns and BLAKE3 takes
68.086 ns. The [CSV](hash-cost-2026-10-25.csv) contains every size/update case,
mean, MAD and coefficient of variation (CV). XXH3's 1 MiB cases have 26.7% and
27.6% CV; do not use those as precise cost ratios. Rapidhash's single-update
64 MiB case has 15.2% CV; its 16 KiB-update case has 2.9% CV.

**K12 implementation caveat:** RustCrypto `k12` 0.5.1 uses `keccak` 0.2.2,
whose default x86 backend is software. Its explicit portable-SIMD backends are
nightly-gated. BLAKE3 and SHA-256 use default hardware dispatch. These measurements
do not establish the speed of an optimized SIMD K12 implementation or a future
vendored port. No ARM, Zen 5, cold-file or parallel hashing measurement was made.

The benchmark pins BLAKE3 1.8.7, sha2 0.11.1, k12 0.5.1,
ascon-hash256 0.1.0, museair 0.6.0 and rapidhash 4.5.1.
Exact zenhash/zenbench revisions and transitive versions are in the
[manifest](../tools/hash-cost/Cargo.toml) and lockfile. The adapters use default
XXH3 seed, Rapidhash v3 default C-compatible secrets, zero MuseAir seeds,
ordinary unkeyed BLAKE3, and empty KT customization strings.

Known-answer examples for SHA-256, BLAKE3, KT128 and Ascon-Hash256 passed.
All eight adapters passed streaming/single-update equivalence across nine chunk
sizes, including 64-, 1024- and 8192-byte boundaries. These are adapter controls,
not exhaustive algorithm validation or a fresh SMHasher run. Formatting and
release Clippy passed with warnings denied.

## Stable wire identity and vendoring

Vendor an implementation of a frozen, externally specified algorithm. Pin the
algorithm revision, output width, seed/key/customization, byte serialization and
EVIF domain framing independently of the crate version. Never use Rust's generic
`Hash` serialization or a crate's evolving default hasher as a file format.
Keep upstream vectors and cross-language vectors covering empty input, block/tree
boundaries, streaming splits, long messages and all canonical sample types.
SIMD and scalar paths must produce the same bytes. Preserve upstream licensing.

[BLAKE3](https://github.com/BLAKE3-team/BLAKE3) has official Rust/C implementations,
a small reference implementation and published vectors. Its 32-byte ordinary
digest is a practical stable choice; acceleration can evolve without changing
identity. [RFC 9861](https://www.rfc-editor.org/rfc/rfc9861.html) provides a stable
definition of KT128 and KT256 (an IRTF Informational RFC). Specify which one and
the customization/output length. KT128 with 32 output bytes targets 128-bit
security; KT256 needs 64 output bytes for 256-bit collision security.

For Ascon, name the final **Ascon-Hash256** algorithm. Older Ascon-Hash v1.2
implementations use different conventions/constants and are not interchangeable;
the [official C implementation](https://github.com/ascon/ascon-c) documents the
transition. Its constrained-device focus does not make it an attractive bulk
pixel hasher in this desktop measurement.

A cryptographic outer hash of XXH3 frame summaries does not make the underlying
pixels cryptographically committed. That requires hashing canonical samples with
the cryptographic function and binding those digests into the media identity.
Keep a full 32-byte crypto digest for conventional 128-bit collision resistance;
truncating it to 64 bits loses that property. Unkeyed hashes do not authenticate
the author of a file. Passing SMHasher is also not a cryptographic guarantee.

## Cross-language availability

SHA-256 has the lowest integration friction: it is in
[Python hashlib](https://docs.python.org/3/library/hashlib.html) and
[Web Crypto](https://www.w3.org/TR/WebCryptoAPI/), as well as mainstream crypto
libraries. SHA-512, SHA-3 and BLAKE2 also have broad library support; they were
not all benchmarked here.

BLAKE3 has official Rust/C, [Python bindings](https://github.com/oconnor663/blake3-py),
[Go](https://github.com/zeebo/blake3),
[JavaScript/TypeScript](https://github.com/paulmillr/noble-hashes),
[Java](https://downloads.bouncycastle.org/java/docs/bcprov-jdk18on-javadoc/org/bouncycastle/crypto/digests/package-summary.html)
and [.NET](https://github.com/bcgit/bc-csharp/blob/master/crypto/src/crypto/digests/Blake3Digest.cs).
It usually requires an added dependency rather than a platform built-in.

K12 is available in RustCrypto, C/XKCP,
[Python/PyCryptodome](https://www.pycryptodome.org/src/hash/k12), noble-hashes
for JS/TS, and Bouncy Castle for Java. Check KT128 versus KT256 availability.
Final Ascon-Hash256 has official C, RustCrypto, and Bouncy Castle Java/.NET
implementations; verify final-standard vectors rather than accepting any library
named Ascon.

[xxHash](https://github.com/Cyan4973/xxHash) has a wide bindings ecosystem, but
support for XXH64 alone is insufficient for XXH3. Rapidhash and MuseAir require
more version/variant scrutiny for wire interoperability. Vendoring fixes our
implementation but does not automatically supply other languages with matching
implementations.
